# AI Usage Disclosure

The event rules require AI assistance to be cited accurately and specifically. This is a
running log, updated as the project is built rather than reconstructed afterwards.

**Tool used:** Claude Opus 5, via Claude Code (CLI/desktop agent).
**Extent:** substantial. The majority of the source code in this repository was AI-generated
from a human-authored specification, then reviewed and directed by the human. This document
records the split honestly rather than minimising it.

- `README.md` — all prose, including the Limitations section.

### Proposed by Claude, decided by the human

- **Re-scoping the 40-hour milestone plan into ~12 hours.** Claude produced the revised budget
  and flagged that the original plan was 31 hours of work against a one-day deadline.
- **Merging M3 (building shadows) into M2 (tree shadows).** Claude's argument: the shade
  pipeline is identical for both geometry sources, so splitting them spends a checkpoint cycle
  for no risk reduction — and a trees-only demo in downtown Portland is a weak demo.
- **Clamping shadow length at low sun elevation.** Claude flagged that `height / tan(elevation)`
  diverges near sunrise and sunset (a 10 m building at 0.1° elevation mathematically casts a
  5.7 km shadow) and proposed a 200 m clamp, disclosed in the README limitations.
- **A Minkowski-sum shadow projection instead of the convex hull.** Claude flagged that the
  convex hull over-fills concave buildings — courtyards and L-shaped notches get filled with
  shade that isn't there — and that the exact swept region is ~12 more lines in Shapely.
  **Raised as a question, not implemented.** The brief's convex-hull approach stands until the
  human decides otherwise.

### Technical decisions Claude originated

- Deriving the demo bounding box from a centre point and a half-extent in metres
  (`config._derive_bbox`) instead of hand-typing four corner coordinates, so they can't drift
  out of sync.
- Exposing that bounding box through `/api/config` so the frontend rectangle and the server's
  routing area have a single source of truth and cannot disagree.
- Writing `scripts/verify_env.py` *before* any application code, on the reasoning that if the
  GeoPandas/Shapely/PyProj stack failed to install on Windows the project was dead and we
  needed to know at hour one, not hour six.
- The Okabe–Ito colour palette choice, the 44 px minimum target size, and the 17 px body text —
  derived from the brief's accessibility requirements but not specified in it.

### Verified, not assumed

The brief instructed that OSMnx and pvlib API details be checked against the installed packages
rather than recalled. Claude ran `scripts/verify_env.py` and confirmed against
**OSMnx 2.1.1 / pvlib 0.15.2 / Shapely 2.1.2 / GeoPandas 1.1.4 / Python 3.13.12**:

- `ox.graph_from_bbox(bbox: tuple, *, network_type=...)` — v2 form: bbox is a single tuple and
  the remaining arguments are keyword-only.
- `pvlib.solarposition.get_solarposition` returns columns
  `apparent_zenith, zenith, apparent_elevation, elevation, azimuth, equation_of_time`.
- `shapely.STRtree` is available, so no extra spatial-index dependency is needed.
- Solar position for Portland at 15:00 on 15 Aug 2026 computes to azimuth 223.4°,
  elevation 51.3° — west-southwest and high, which is correct for an August afternoon.

**Still unverified at the end of M0:** the *ordering* convention inside the `graph_from_bbox`
bbox tuple. The type signature doesn't reveal it. This will be confirmed empirically in M1 by
inspecting the coordinates of the downloaded nodes, not by trusting a docstring.

### Post-M0 audit round

After the first M0 commit, a second AI pass (a Claude sub-agent acting as a production-readiness
reviewer) audited the changeset for accessibility, correctness and honesty. Its findings were
checked by hand before being acted on, not accepted on trust. What it caught that the first pass
missed:

- **A real WCAG AA failure the automated sweep structurally could not see.** The destination map
  pin is white bold 16px text on `#d55e00`, which is **3.87:1** against a 4.5:1 requirement.
  The first contrast sweep ran before any pin existed in the DOM — pins are Leaflet `divIcon`
  elements created only after a point is placed. Verified the ratio by hand, then darkened the
  pin fill to `#a34700` (6.07:1). Full-strength `#d55e00` is retained for M2 route lines, where
  the 3:1 non-text threshold applies.
- **A self-contradiction between two files.** A comment in `app/config.py` claimed the bbox tuple
  ordering had been "verified by scripts/verify_env.py", while this file correctly recorded it as
  unverified. The claim was false — a type signature says nothing about element order. Comment
  corrected. Given the brief's honesty requirement, this was treated as a blocker.
- **Two README overclaims.** The accessibility section promised "nothing smaller than 15px,
  targets at least 44px" while Leaflet's attribution rendered at 11px and its zoom buttons at
  26px; and it described colour-independent route lines in the present tense when no routes exist
  until M2. Fixed on both sides: Leaflet's controls were enlarged to 44px and its attribution to
  13px, and the README now separates what works today from what is scheduled, naming the 13px
  attribution as an explicit exception.
- **A live-region bug.** The "next click will move A" message was hardcoded, so after re-placing
  A it named the wrong point — and that live region is the only channel carrying this state to a
  screen-reader user.
- Also fixed: `role="application"` removed from the map (it drops AT out of browse mode without
  custom key handling to justify it), `prefers-reduced-motion` extended to Leaflet's JS-driven
  inertia and zoom animations that CSS cannot reach, coordinate inputs switched off
  `type="number"` (an arrow-key press silently moved a point 110 km), `aria-invalid` and
  `aria-describedby` wired to validation failures, `/health` now reports `degraded` instead of
  `ok` when the geo stack is absent, `verify_env.py` made robust to the broken-install case it
  exists to diagnose and its output made pure ASCII for Windows consoles, and `run.py --reload`
  scoped to `app/` and `web/` instead of watching `.venv`.

**One fix introduced a bug that testing then caught.** The first attempt at forcing repeat
live-region announcements used `requestAnimationFrame`, which never fires in a tab that isn't
compositing — leaving the status line permanently blank. Replaced with a synchronous
alternating zero-width space. Recorded here because "the AI wrote it and it was verified" and
"the AI wrote it and it worked first time" are different claims, and only the first is true.

**Known gap accepted, not fixed:** below 860px the map still captures touch drags that were
meant to scroll the page. Documented in the README and scheduled for M5 rather than half-fixed
under time pressure.

### Second audit round — verifying the fixes

The fix commit was itself audited. It had introduced a regression: switching the coordinate
inputs from `type="number"` to `type="text"` silently orphaned the `input[type="number"]` style
block, so all four fields fell back to browser defaults — **13.3px text in 21px-tall boxes**,
against a README that claims a 15px floor and 44px targets. Confirmed in the live page before
fixing (measured 13.3333px / 21px), then bound the styling to `.point-row input` so it can't be
broken again by changing an attribute. Fields now measure 16px in 45px boxes.

That is the second time in this project that an AI-authored fix introduced a defect that only
testing caught. Both are recorded here rather than quietly corrected, because the accuracy of
this disclosure is the point of it.

Also fixed in this round: the input border used a decorative `#c9cfd6` (1.57:1) where a form
control boundary needs 3:1, so a dedicated `--field-border` token at 4.83:1 was added; `#map`
regained `role="region"`, because ARIA does not allow naming a bare `<div>` and removing
`role="application"` had left its label potentially unexposed; validation marking moved out of
`setPoint` so a rejected *map click* no longer paints the typed coordinate fields red while they
hold a value we accepted; and two README statements were corrected — a quoted script output line
that no longer matched after the ASCII change, and a claim that the map pins were covered by the
automated contrast sweep when they were in fact checked by hand.

## Milestone 1 — 16 August 2026

### Generated by Claude

- `app/graph.py` — download, disk cache, nearest-node lookup, route geometry and length.
- `scripts/warm_cache.py` — pre-download plus the empirical bbox-orientation check.
- `/api/route` in `app/main.py`; the routing UI, results panel and route rendering in
  `web/index.html`.

### Decided by the human

- The go-ahead to start M1, and the scope decisions recorded above.

### Two things resolved by measurement rather than assumption

**The bbox tuple ordering — the last unverified assumption from M0 — is now settled.** The
downloaded graph's nodes span lat 45.51302–45.53098, lon −122.68781–−122.66223, which is exactly
the requested box, confirming `(west, south, east, north)` is correct for OSMnx 2.1.1. This is
checked in code (`graph.verify_bbox_orientation`) rather than in a comment, so it re-runs on any
fresh download and raises if a future version changes the convention.

**A new dependency was avoided rather than added.** `ox.distance.nearest_nodes` raised
`ImportError: scikit-learn must be installed as an optional dependency to search an unprojected
graph`. The brief requires asking before adding a dependency not listed in §4, and scikit-learn
is a large addition for one nearest-neighbour lookup. Replaced with a vectorised NumPy scan over
the ~3,400 nodes, with the longitude term scaled by cos(latitude) so the search isn't biased
east-west. Exact, microseconds, no new dependency, nothing to ask about.

### Honesty notes

- Walking duration is displayed with its assumption stated in the UI (1.1 m/s, a comfortable
  older-adult pace) and labelled as an assumption, not a measurement.
- The results panel reports "In shade: not measured yet (Milestone 2)" rather than omitting the
  row or showing 0%, either of which would read as "this route has no shade".
- The API returns `shade_fraction: null` for the same reason.

## Milestone 2 — 16 August 2026

### Generated by Claude

- `app/sun.py` (solar position, shadow offsets, clamping), `app/shade.py` (the shade model),
  `app/places.py` (named destinations), `scripts/check_shade.py` (the verification suite).
- `/api/route` rewritten to return both routes; `/api/places` added.
- `web/index.html` rebuilt: dark mode, place search, geolocation, Surprise me, time controls,
  shade-preference slider, dual route rendering and the comparison panel.

### Requested by the human

- Dark mode, an interface that does not require knowing coordinates, a "surprise me" action,
  and location detection. Address entry was already required by §8 of the brief.

### Verified by measurement, not assumed

`scripts/check_shade.py` exists because a shadow pointing the wrong way still renders as a
perfectly nice picture. It checks that morning shadows fall west and afternoon shadows fall
east, that a lower sun casts a longer shadow, that the clamp bites, that every shade fraction
lands in 0..1, and that shade routing at aversion 0 reproduces the shortest path exactly.

**One check failed and the code was right — the test was wrong.** An assertion that the midday
sun sits due south at 12:00 failed with azimuth 147.6°. That is correct behaviour: Portland is
about 17.7° west of its timezone's central meridian, which pushes solar noon to roughly 13:07,
and the equation of time moves it further. The test was rewritten to *find* the daily maximum
instead of assuming its clock time; it lands at 13:15 with azimuth 180.03°, which is a much
stronger check because it validates the timezone and equation-of-time handling rather than
merely agreeing with a guess.

### Two problems hit and fixed during this milestone

**An eight-query design got the project rate-limited.** The first `places.py` issued one
Overpass request per category. Overpass responded with connection timeouts. Rewritten as a
single combined query — OSMnx ORs a multi-key tag dict into one request — and the result is now
cached to `cache/places.json` so it is fetched at most once ever rather than once per process.

**Overpass then went unreachable for about half an hour**, which was not our doing: a direct
POST from Python succeeded in 0.9 s while OSMnx's identical query timed out, and the service's
own status endpoint reported two free slots. It recovered on its own and returned 256 features
in 8.2 s. This is recorded because it is the single largest live-demo risk in the project, and
it is why `scripts/warm_cache.py` now pre-caches the network, the places and the shadows.

### An accessibility regression caught by sweeping both themes

The first dark theme overrode the map pin colours, darkening them to 4.07:1 and 4.49:1 against
their own white labels. Pins sit over map tiles rather than the page background, so their fill
must clear 4.5:1 against *white* in either mode — darkening them was exactly backwards. The
overrides were removed and both themes now sweep clean at 65 text nodes each.

### Honesty notes

- The headline reads "+5 min walk, 94% shaded instead of 29%". Every one of those numbers is
  computed: percentages from measured intersection length against modelled shadow geometry,
  distance and time from the routed path.
- **No temperature claim is made anywhere**, per §7.
- The result panel names its inputs — "modelled from 1,186 building shadows, 737 tree shadows
  and 16 park areas" — so a judge can see what the number rests on.
- Walking time still carries its 1.1 m/s assumption in the UI.
- When the sun is below the horizon the UI says so and both routes are reported as identical,
  rather than silently returning 0% shade as if it were a measurement.

### M2 audit round

A production-readiness review of the M2 changeset confirmed the shade maths independently
(including that `dx = L·sin(azimuth+180)`, `dy = L·cos(azimuth+180)` is the correct projection
for an azimuth measured clockwise from north) and found four real defects, all fixed:

- **The headline number was read off the wrong edge.** `route_shade_fraction`,
  `route_length_m` and `route_coordinates` all defaulted to `weight="length"`, but the shadiest
  route is chosen by `shade_cost`. Where two nodes are joined by several parallel ways, the
  cheapest-by-length edge is not necessarily the one Dijkstra took, so the reported shade,
  length and drawn polyline could all come from a road the walker was never routed along —
  systematically under-reporting the one figure the project is judged on. `weight` is now
  threaded through all three.
- **A concurrency hazard that produced wrong numbers rather than crashes.** `annotate_graph`
  writes `shade_cost` onto the process-wide graph, and `/api/route` is a sync endpoint, so
  FastAPI runs it in a threadpool. Two browser tabs at different slider settings could
  interleave, returning a route computed against the other request's settings. Now guarded by a
  lock. Verified with six concurrent requests alternating aversion 0 and 3: every response
  matched its own setting.
- **A torn read in `_node_arrays`**, which published its guard variable before the arrays it
  guards. First-request-only and a tiny window, but a real `TypeError`. The guard is now
  assigned last.
- **Three Overpass responses were being downloaded twice.** `shade._fetch` never called
  `configure_osmnx`, so the cache folder depended on which module ran first; `check_shade.py`
  wrote to `cache/` while the server wrote to `cache/osmnx/`. Confirmed on disk, fixed, and the
  duplicates deleted. This re-incurred the exact Overpass exposure documented above.

Two accessibility issues in the same pass: the busy state used `disabled`, which moves focus to
`<body>` and dumps a keyboard user to the top of the document mid-request (now `aria-busy` plus
a re-entrancy flag); and the shade bar rendered "0%" with an `aria-label` reading "0% of this
route is in shade" when the sun was down — which contradicted this file's own claim two
sections above. It now reads "no sun to measure" and the bar is not drawn at all. The shade bar
fill was also darkened from 3.05:1 to 6.58:1.

Three README statements were corrected against the code: a line listing route line-patterns as
unbuilt when they were built, a data-sources table presenting benches, steps and Open-Meteo as
live when nothing references them, and a cache table that omitted the per-edge shade pass being
memory-only.

## Visual design pass — 16 August 2026

### Requested by the human

"Make it Apple Liquid Glass style for all the buttons and more."

### Generated by Claude

The complete restyle of `web/index.html`: Liquid Glass surfaces, pill buttons, the system font
stack, Apple easing curves, a pointer-tracked specular highlight, and a background wash for the
glass to refract. Claude also decided which parts of Apple's language to *reject* — the
120–200px section rhythm and the large display type scale belong to marketing pages, and would
have wrecked a dense control panel used by someone who is 71.

### Where accessibility overrode the aesthetic

Three measured findings each changed the design rather than being noted and ignored:

1. **The background wash was too strong.** At the first values the three washes composited to
   rgb(198,211,203) where they overlapped, dropping 15px secondary text to **4.36:1** — below AA
   — anywhere the sidebar showed the page through. Reduced roughly threefold.
2. **Dark-mode glass compounded.** Wash plus a 7% white fill plus the gloss lifted card
   backgrounds to rgb(59,76,73), taking Apple's own `#a1a1a6` secondary grey down to **3.5:1**
   across thirteen elements. Fixed by reducing the wash and the gloss rather than by abandoning
   the grey.
3. **Glass covered 32% of the viewport**, past the 25% ceiling in Apple's own guidance, and
   stacked five glass cards down one sidebar — the "every card is a glass card" failure mode.
   The input cards were made solid, bringing glass to 13% and concentrating it on the header,
   the buttons and the result.

Secondary text in light mode is `#5b5b60` rather than Apple's `#6e6e73`: the exact value passes
at 4.6:1 but with no margin over a translucent surface, and the target user is 71.

### A verification bug that was producing false passes

The contrast sweep used for every previous milestone read the *token value* of an element's
background. That is correct for opaque surfaces and **wrong for translucent ones** — it reports
`rgba(255,255,255,0.07)` as if it were white. Rewritten to composite the real stack: page
surface, background wash, translucent fill, gloss.

The first rewrite still had a defect of its own: colours were parsed with a bare digit regex, so
the hex token `#000000` parsed as `[0, NaN, NaN]` and **every dark-mode result came back "0
failures" while being meaningless**. Once hex parsing was added, dark mode showed thirteen real
failures. This is recorded because a verification tool that silently passes is worse than no
tool, and it had been reporting success for two full rounds.

A third artefact was chased down and dismissed rather than "fixed": two buttons appeared to fail
at 1.38:1, but they sit inside a closed `<details>`, and computed styles for render-skipped
subtrees are stale. Opening the section and letting style settle showed them correct. The sweep
now opens it before measuring.
